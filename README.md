# Ausbildung Hunter AI

A production SaaS that helps people in Germany find and apply for **Ausbildung** (vocational training) and **Arbeit** (jobs). Users connect their own Gmail/Outlook account, compose and send applications in bulk with a fair daily quota, use an AI assistant for application support, scan their own documents for fit, and search real German vacancies with a deterministic match score.

Via the CLI: `npx supabase db push` (or paste into the SQL editor). The migrations create all tables, RLS policies, storage buckets, triggers, and the invitation seeds.

**Auth configuration (required for the email-confirmation flow):**

1. **Auth → URL Configuration**: set **Site URL** to your app URL and add **`https://<your-domain>/auth/callback?next=/onboarding`** to **Redirect URLs**.
2. **Auth → URL Configuration → Flow type**: must be **PKCE** (default for new projects). The app clients are configured for PKCE (`flowType: "pkce"`) — an implicit-flow project cannot complete the code exchange in `/auth/callback`.
3. **Authentication → Providers → Email**: enabled, with **Confirm email** on.

Create the two private storage buckets if not created by a migration: `application-attachments` and `ai-files` (both **private**, `user_id`-scoped policies).

## How the key systems work

### Quota model (atomic, no race conditions)

- Registration with `DRIF928` creates a profile with 0 daily emails; `DRIF089` creates one with 100/day and records a `user_quota_upgrades` row.
- Each send campaign **reserves** quota with `FOR UPDATE` on the user's `daily_usage` row; the reservation is released if the campaign fails to be created. There is no read-then-write race.
- The worker endpoint (`/api/internal/email-worker`) claims messages with `FOR UPDATE SKIP LOCKED`, so multiple workers never double-send. Retries are bounded; Microsoft calls use `Idempotency-Key` to stay safe on retry.
- **Requirement:** the worker endpoint is passive — it processes messages when called. For production you need a durable trigger (cron, queue, or always-on service) that calls it periodically. This is the main known gap for unattended sending.

### AI usage

- One shared `daily_usage.ai_requests` counter, capped at 100/day, reserved atomically before any AI call (assistant, scanner). AI failures do not permanently burn quota; the reservation is released on error.

### Opportunities search (Phase 3)

The search is built around what the BA REST API actually supports, and never pretends otherwise. Two retrieval modes:

- **`upstream`** — true provider pagination. Used for the plain case (goal, keyword, location/radius, `today` freshness, relevance order). The API is asked for exactly one page per request and `total` is the source's own `maxErgebnisse`.
- **`scan`** — a bounded server-side window (≤ 10 pages × 50 items = 500 listings). Used whenever the request needs a capability the API cannot express: role/company post-filters, `14d`/`30d` freshness, non-relevance sorting, or employment/training-type/home-office/salary/distance filters. The full window is collected **before** filtering/sorting (so the order isn't biased by where a page happens to fall), deduped by stable id, and cached page-independently — turning pages never re-hits the provider. If the 500-item budget ends before the source does, the response is marked `scan_truncated` and the UI says so instead of hiding it.

**Filters** are only offered when backed by real provider data. The BA parameters that were verified non-functional (`arbeitszeit` remote, `beruf` role, `arbeitgeber` company) are **never sent** to the API; role/company are applied server-side on the source's occupation fields, and home-office/employment on the source's flags. Home-office and training-type filters are Ausbildung-only (the source does not document them on job postings); requesting them for Arbeit returns a clear 400. Distance sort / max-distance require a location (400 otherwise).

**Sorting** is deterministic and null-safe: `relevance` = source order; `newest`/`oldest` by source `posted_at`; `salary` by the source's numeric amount; `distance` by the source's km; `match` by the user's per-user match (see below: complete matches by score descending, incomplete matches after all complete ones — unknown data is never ranked as a perfect match; falls back to relevance when no match is requested or no profile exists). Items missing the sort field sort **last** (never a guessed value), ties broken by stable id.

**Pagination** respects the source's ~10,000-item bound: `page` ≤ 200 and `pageSize` ≤ 50 (200 × 50 = 10,000). Beyond that the API returns empty pages, so the UI shows a "source bound reached" message rather than faking deeper results.

**Freshness** is explicit: `today` is applied by the API itself (`veroeffentlichtseit=1`); `14d`/`30d` are applied server-side on the source's publication date within the scan window; everything else is `any`. Undated listings are excluded from date filters (never guessed).

**Shareable URL state** is a strict whitelist (`goal`, `q`, `role`, `company`, `location`, `radius`, `freshness`, `sort`, `employment`, `training_type`, `home_office`, `salary`, `distance_max`, `page`, `match`). Anything else — including anything resembling an id or token — is dropped; `q` maps to keyword; invalid values normalize to defaults; a missing/invalid `goal` drops the whole state. URL state is only ever used for **filtering**, never for authorization. Detail pages carry a `from` param so "back" returns to the exact search (same filters + page).

**Cache + matching independence** (enforced, tested): the `opportunity_cache` key is fully user-independent (schema version + mode + hash of the provider query; `match` excluded) and stores only normalized source data (a `window` with `match: null`, `total`, `scan_truncated`, `exhausted`). The per-user match is computed **after** the cache read, attached in-memory only, and never written back — two users searching the same query share one source row and no user data can leak between them.

### AI Ausbildung Search (`/opportunities/ai-search`)

Profile-driven search over the same public source, with live progress and an Excel export:

1. **Profile first** — the pipeline reads the user's latest validated `candidate_profiles` row (created by the Bewerbung Scanner; same lookup the matcher uses). No profile → the UI routes the user to the scanner first (or to the AI Search CTA after a scan completes). The profile is never browser-supplied.
2. **AI plans, source executes** — exactly **one** AI call (one atomic `reserve_ai_request`) turns profile *facts* (target roles, keywords, locations, preferences) into 1–5 bounded queries. The plan is strictly Zod-validated (`aiSearchPlanSchema`, strict objects); any garbage or oversized field rejects the plan with a controlled retry message. The AI **never contributes opportunity content** — every row comes from a real source (BA Jobsuche or a discovered public page).
3. **Deterministic collection** — each query runs through the existing `searchOpportunities` (shared provider + versioned cache; `upstream` mode paginates, `scan` mode is a single page-independent window), deduped by the stable `provider:external_id` key, capped at an enrichment budget of `target + 10`.
3a. **Web discovery layer (optional, server-only)** — when configured, the plan's web queries additionally run against the **official Tavily Search API** (`src/lib/web-search`, `POST https://api.tavily.com/search`): the server-side key `TAVILY_API_KEY` is the ONLY credential this layer reads and is never exposed to the browser. Requests are hard-capped at **3 Tavily requests per search operation** — one broad request per planned query, each returning many results (no per-source and no per-company requests in this phase). Result URLs come **exclusively from the provider response** — never generated text, so nothing can be invented — and each result is classified by its OWN domain against the Source Registry (registry source → that source's category; social host → social media; other portal host → job portal; remaining non-portal host → possible company career page). `results[].title/url/content/score` are kept, duplicates are removed by normalized URL and by (domain, title), and a small in-memory TTL cache avoids repeating identical requests. Discovery covers publicly indexed results, job portals, company career pages and public social pages: no logins, no private content, no CAPTCHA/authentication/robots.txt/anti-bot bypass (blocked pages are skipped and counted, never worked around). Pages are visited with the guarded fetcher (robots.txt respected), extracted in bounded AI batches with strict anti-fabrication URL cross-checks, then merged with the BA rows by the multi-source dedupe (most authoritative source wins; `source_type` + `additional_sources` provenance kept). If Tavily fails the failure is surfaced honestly (`[TAVILY]` logs + `providerErrors` in the UI) with **no fallback to another provider**; without a key the web layer is skipped — BA results still work.
4. **Detail enrichment** — the shortlist is re-fetched from the source's details endpoint (bounded concurrency 6) to obtain the published description, contact person/email/phone, application URL, requirements, education requirement, and a strictly parsed application deadline (`Bewerbungsfrist/Bewerbung bis` + real calendar date only — never inferred). Dead postings are skipped, never substituted.
5. **Ranking** — the documented match order (complete by score desc → incomplete → unmatched) over the *enriched* rows, sliced to the user's choice (10 / 25 / 50 / 100).
6. **Progress** — `POST /api/opportunities/ai-search` streams newline-delimited JSON events (`profile` → `plan` → `web_status`/`discover`/`check`/`extract` (web layer) → `search` → `enrich` → `dedupe` → `complete` / `error`) with the same plain-text streaming pattern as `/api/ai/chat` (CSP-safe, no inline scripts). The client renders a live progress panel with per-source-category counters and a cancel button.
7. **Excel export** — `POST /api/opportunities/ai-search/export` accepts the validated plan + goal + count and **re-runs the deterministic pipeline server-side** (search windows are cache-warm; no AI call, no quota), then writes a two-sheet workbook with `exceljs` ("Opportunities" with the documented source fields — company, title, location, Bundesland, start date, deadline, email, phone, company website, application URL, source URL, source type, additional sources, requirements, other useful information — plus "Search details" with the plan and provenance). Missing source data is an empty cell, never a placeholder. Same contract as saving: no client-supplied opportunity data is trusted.
8. **Protection** — new `ai_search` rate-limit scope (4/min per user, Postgres-backed like all others); auth + active-status check before any work; BA upstream errors surface as controlled messages.

### Matching Engine (production, Phase 7 — matcher v3)

`src/lib/opportunities/matching/` — a deterministic, explainable, **server-side** matcher that compares the authenticated user's **validated** candidate profile (from the Bewerbung Scanner) against the authoritative, server-re-resolved opportunity. Pure function: same profile + same opportunity = same result; no AI, no LLM-generated reasons, no network, no randomness, no wall clock (experience year math references the opportunity's fixed `retrieved_at`). The engine never invents candidate facts, opportunity facts, requirements, or reasons.

**Architecture:** `candidate profile → normalize → evaluate dimensions → calculate evidence → calculate score → classify match → return explanation`. Modules: `types.ts` (result shape + documented weights), `text.ts` (umlaut-folding normalization, CEFR, language synonyms, dates, "N Jahre" extraction), `profile-normalizer.ts` (validated profile → normalized candidate with per-field provenance), `dimensions.ts` (twelve independent evaluators), `scorer.ts` (inferred cap, completeness, weighted score, hard cap), `explanations.ts` (German UI labels), `index.ts` (`computeMatch` / `matchOpportunity` / `applyMatch`).

**Dimensions** (each yields `match` / `partial` / `mismatch` / `unknown` / `not_applicable`, plus factual German evidence, a missing-information list, and short raw quotes of the documented **candidate-side** and **opportunity-side** values — `null` when a side documents nothing, never invented):

| Dimension             | Weight | Semantics (documented in code)                                                                                                                                                                                                                                                                                 |
| --------------------- | ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Goal / eligibility    | 18%    | **Essential.** Candidate goal vs opportunity type (Ausbildung eligibility). Conflicts are a real `mismatch` — never silently converted.                                                                                                                                                                        |
| Role                  | 20%    | **Essential.** Target roles / preferred titles vs title, `hauptberuf`, alternative professions. **Graded, deterministic similarity (v3):** exact normalized phrase or containment → 1.0 (`match`); otherwise the weighted content-token overlap ratio (full token hit = 1.0, German compound suffix relation with both tokens ≥ 6 chars = 0.5, e.g. `Industriekaufmann`≈`kaufmann`), which becomes the graded contribution — distinct professions yield distinct scores. No semantic similarity beyond documented overlap is claimed. |
| Education requirement | 20%    | **Essential for Ausbildung.** German school hierarchy (`basic < intermediate < advanced < university`); a documented higher qualification satisfies a lower documented requirement. Unclassifiable source requirement → `unknown` (fail-safe). Explicitly contradictory requirement hard-caps the score at 30. |
| Skills                | 14%    | Required vs preferred, separated. **Graded (v3):** contribution = documented required-skill coverage (matched / required). Missing candidate info is never a negative; no documented requirement → `not_applicable`.                                                                                          |
| Experience            | 9%     | Only explicitly documented "N Jahre Erfahrung" statements; documented years computed from dates vs the record's `retrieved_at` (deterministic). No years are ever inferred. **Graded (v3):** contribution = min(1, documented years / required years).                                                            |
| Languages             | 9%     | CEFR A1–C2 comparison (higher satisfies lower; native ≈ C2). Inferred levels stay inferred. A **required** language (e.g. German) missing from the profile → `unknown` → incomplete (not a negative).                                                                                                          |
| Location              | 4%     | Same documented location → `match` (1.0); no candidate location → `unknown`. **v3:** a documented **difference** is a scored `mismatch` (contribution 0) — the documented location requirement is not met; the relocation dimension separately documents willingness (it can soften, never undo, the documented fact). |
| Relocation preference | 2%     | Only when a move is required (documented different locations): willing → `partial` (generic willingness, not city-specific), unwilling → `mismatch`, **unknown → `unknown`, never incompatible**. No move required → `not_applicable`.                                                                         |
| Remote / home office  | 1%     | Only when the source documents home office; missing → `not_applicable`/`unknown`, never incompatible.                                                                                                                                                                                                          |
| Employment type       | 1%     | The profile schema documents no working-time preference → always `unknown` when the source documents a type (honest, not guessed).                                                                                                                                                                             |
| Training type         | 1%     | The source documents the Ausbildungsform (e.g. `AUSBILDUNG`, `DUALES_STUDIUM`); the profile schema has no training-type preference field → `unknown` (non-essential, never blocking) when documented, `not_applicable` otherwise.                                                                              |
| User preferences      | 1%     | Candidate industry preferences vs the opportunity's industry. The BA source documents **no industry field** → `unknown` (non-essential) when the candidate documents preferences, `not_applicable` otherwise.                                                                                                  |

**Result states** (`MatchResult`): `complete` (every essential dimension evaluated → integer score 0–100), `incomplete` (a profile exists but an essential dimension is `unknown` → **no score is produced**; UI shows "Match unvollständig" and lists exactly what is missing — e.g. education, German language level, location preference), `unavailable` (no candidate profile → no score, no dimensions). Essentiality is per (profile, opportunity): goal + role always; education for Ausbildung; languages when the source documents a requirement. Missing information is **never** converted into a fake positive or negative — `unknown` contributes 0 to nothing and is surfaced in `missing_information`.

**Scoring:** each evaluated dimension contributes a share of 0..1 — a **graded `contribution`** when the dimension documents a continuous degree (v3: role similarity ratio, required-skill coverage, experience-year ratio, documented location mismatch = 0), otherwise the coarse status share (`match` = 1, `partial` = 0.5, `mismatch` = 0) — and the weighted sum is **renormalized over the evaluated dimensions only** (`unknown` / `not_applicable` are excluded, so missing data neither inflates nor destroys the score and never counts as a match). **Inferred-data cap:** any dimension whose candidate-side evidence is AI-extracted (not user-confirmed) is capped at `partial` with its graded contribution capped at 0.5, with a provenance note — inferred information is never scored as confidently as explicit information. **Hard cap:** an explicitly documented, explicitly contradictory education requirement caps the score at 30. Every `reasons` line is a factual evidence sentence from the data — no generated marketing copy. The full per-dimension breakdown (status, graded share, evidence, quotes, missing information) is returned in every `MatchResult` and rendered on the detail page.

**Saved match snapshots + staleness (migration 12):** saving an opportunity stores a **server-computed** saved-at snapshot: `match_score` + `match_status` (migration 9/10) **plus** `matcher_version` (engine version) and `match_profile_updated_at` (profile revision at snapshot time). This lets the UI distinguish three states that are never conflated: **current match** (always recomputed live, server-side, on the detail page), **historical snapshot** (the stored values, labeled with their "Stand" date and matcher version), and **incomplete snapshot** (no score — never a guess). If the profile's current revision is newer than `match_profile_updated_at`, or the engine version advanced, the saved page and detail page explicitly state the snapshot may be stale — a profile change never masquerades silently as current data.

**Integration:**

- **Search** (`/opportunities` with matching enabled): the per-user match is computed **after** the shared-cache read and attached in-memory only — cards show score + short reason when complete, or the incomplete state with the top missing facts when data is insufficient. `sort=match` ranks complete matches by score (incomplete ones never ranked as matches). The cache key and cache content remain **user-independent** (tested).
- **Detail page** (`/opportunities/[id]`): overall match state, score only when valid, dimension-by-dimension explanation with status icons, evidence sentences, candidate/opportunity quotes, consolidated missing information, and — when the opportunity is saved — the labeled historical snapshot with staleness reasons.
- **Saved page** (`/opportunities/saved`): per-card snapshot with "Stand" date, matcher version, and an explicit "Snapshot veraltet" badge + factual reasons when the profile or engine changed since.
- **Dashboard**: a safe matching summary — saved/complete/incomplete counts and the top 3 **complete** snapshots (historical, labeled as such). Without a candidate profile it shows a warning instead of a fake ranking.

### Application prefill (Phase 6)

`src/lib/opportunity-prefill.ts` — server-side prefill that carries an opportunity into the application composer. "Prepare application" is linked from the opportunity detail page and from every saved-opportunity card; both point to `/applications/new?opp=<key>` where the key is the URL-encoded opportunity id (`<provider>:<reference>`).

**Flow** (entirely server-side; the browser only ever submits the key): authenticated user required → the key is validated against the provider schema **before any network call** → the opportunity is **re-resolved from the authoritative BA source** (never from URL/browser data, never from the cache) → `buildOpportunityPrefill` derives subject and body from **documented fields only** (profession, company, location, reference — missing fields drop out, nothing is invented) → applied to the user's draft per the strategy below.

**Prefill content:** subject is `Bewerbung um einen Ausbildungsplatz als <Beruf> (Referenz <nr>)` (Ausbildung) or `Bewerbung als <Beruf> (Referenz <nr>)` (Arbeit), with factual generic fallbacks when profession or reference is undocumented; the body is a short, neutral German cover-letter skeleton in which every interpolated source string is HTML-escaped. **Recipient derivation:** the opportunity's contact email is pre-filled **only when documented by the source and it passes the same validation as manually added recipients**; otherwise the draft opens without a recipient and the user adds one.

**Draft selection strategy** (never destroys work):

- active draft is **blank** (no subject/body, no recipients, no attachments) → the prefill is written into it **in place**;
- active draft has **content** → a **new pre-filled draft** is created and becomes the active one; the previous draft is kept untouched, and a notice explains this to the user.

**Persistence (migration 11):** four nullable context columns on `application_drafts` (`opportunity_key`, `opportunity_title`, `opportunity_company`, `opportunity_source_url`) record which opportunity a draft was pre-filled from. They are display/context only — subject, body and recipients remain fully user-editable — and the composer shows a "prepared from" card with a link back to the opportunity detail. RLS is unchanged: the existing user-scoped draft policy already covers the new columns.

**Failure modes:** malformed or foreign key → `invalid_key` (no network call, no database write); the source no longer lists the vacancy (e.g. `STELLENANGEBOT_NICHT_GEFUNDEN`) → `unavailable` with a clear German error, no draft write.

**Usage & AI status**: email usage comes from the server-side quota RPC (`getUsageSnapshot` — reserved + sent, quota upgrades included); AI usage uses the shared `AI_DAILY_REQUEST_LIMIT` constant (single source of truth with the quota RPCs). No quota logic is duplicated, no browser-provided values are trusted.

**Activity**: existing `activity_logs` system, now also logging `opportunity_saved` / `opportunity_removed` (best-effort — a failed audit insert never fails the user action). No sensitive content is logged.

**Performance**: all dashboard reads run in parallel batches; the recommendation search is one bounded window (6 items) reusing the shared user-independent cache; no per-opportunity provider calls.

**Navigation** (all authenticated, all real routes): Scan `/bewerbung-scanner` · Find `/opportunities` · AI `/ai` · Saved `/opportunities/saved` · Email `/settings/email` · Usage `/settings/usage` · New application `/applications/new` · Campaign `/applications/campaign/[id]` · Opportunity `/opportunities/[id]`.

### Billing, Plans & Admin (Phase 10)

`src/lib/billing/` + `supabase/migrations/20261001000000_billing_and_admin.sql` — the production SaaS billing/admin foundation, **without a payment provider** (none is configured; no provider credentials, prices, or billing data are invented).

**Plans & entitlements** (`plans.ts`, `entitlements.ts`, `billing_plans` table): the plan catalog (`free` / `plus` / `pro`) is stored in `billing_plans` (single source of truth for limit values, read by both the quota SQL and the TS layer). `getEntitlements(userId)` resolves the effective plan **server-side** from the user's persisted subscription row: active + period unexpired → plan limits; canceled/expired/missing → **Free** (most restrictive; a failed lookup also fails closed to Free, never to an upgrade). Free-plan limits equal the pre-Phase-10 defaults (50 emails/day, 100 AI/day) — guarded by tests, so free users see zero behavior change.

**Usage-limit integration** (no duplicated quota logic): the email limit flows through the existing `effective_daily_email_limit()` SQL function (replaced in migration 13): the plan base now **floors** the profile base, and invitation-code quota upgrades still apply as the max — `reserve_email_capacity` / `get_daily_usage_snapshot` / campaign creation are unchanged in code. The AI limit: `reserve_ai_request` is now called with the entitlement's `aiPerDay` (scanner + AI assistant), still enforced by the same quota RPC. **No browser input ever influences plan, quota, or entitlement.**

**Subscription state** (`subscriptions` table): per-user row with plan, status (`active`/`canceled`/`expired`), provider, period, cancellation timestamp, and the granting admin. RLS: **select own row only — no user insert/update/delete** (only the service-role admin layer writes).

**Provider abstraction** (`provider.ts`): `BillingProvider` interface (activate/cancel/verifyWebhook) with a single implemented `manual` provider that reports `configured: false`. The webhook route (`POST /api/billing/webhook`) therefore **always answers 501 `billing_provider_not_configured`** — it never validates, never mutates, and never pretends to speak a provider protocol. The billing UI (`/settings/billing`) shows the explicit not-configured state, the current plan, plan-base limits, effective email limit (incl. upgrades), and subscription details.

**Admin foundation** (`admin.ts`, `admin-users.ts`, `/admin`, `/api/admin`): membership in `admins` (RLS enabled, **no user policies** — users cannot read or write it, so self-elevation is impossible). `requireAdmin()` verifies session + membership server-side; the **actor always comes from the session**, the **target from the URL**. Admin actions (`set_plan`, `reactivate_subscription`, `cancel_subscription`, `grant_admin`, `revoke_admin`) use strict Zod schemas (any injected field → 400), write via the service role scoped to the exact target id, and append an immutable row to `admin_audit_log` (actor, target, action, details; service-role only). Self-revocation is blocked (lockout guard). The admin UI lists users (bounded 50, email filter) with plan, today's usage, and role — no tokens, secrets, or storage paths are ever exposed.

**First admin bootstrap** (manual, documented — no self-service): apply migration 13, then `insert into public.admins (user_id) values ('<your-user-uuid>');` in the Supabase SQL editor.

### GDPR Data Controls & Sending Reliability (Phase 11)

A complete product audit (32 areas: RLS, routes, storage, billing, worker, error boundaries, indexes, GDPR, deployment) surfaced two production-critical gaps for a German SaaS holding personal data (applications, encrypted email credentials, AI files): **no GDPR portability/erasure**, and **campaigns that can be stuck forever after a worker crash**. Phase 11 closes both — no migration was required (existing FK cascades, storage buckets, and quota RPCs are reused).

**Data export** (`GET /api/account/export`, `/settings/data`): a server-side JSON export of everything the account holds — profile, candidate profile, saved opportunities, drafts, campaigns + messages, AI conversations/messages, scans, subscriptions, daily usage, activity log — plus a _metadata-only_ storage inventory. OAuth tokens, encrypted credentials, and API keys are structurally excluded (their tables are never queried). The user id comes from the session only.

**Account deletion** (`POST /api/account/delete`): strict schema (any extra field → 400) + typed-email confirmation verified server-side against the session profile (case-insensitive). The order is all-or-nothing: (1) `application_drafts` first — that `sender_email_account_id` FK is `ON DELETE RESTRICT` against `email_accounts` and would otherwise block the cascade; (2) `auth.admin.deleteUser` — Postgres cascades all 21 user-FK tables; (3) per-bucket storage sweep (path-prefixed to the user, batched). If a database step fails, storage is untouched — no partial deletion, and the API answers 500 "account unchanged".

**Stale-campaign recovery** (`recoverStaleCampaigns` in `email-campaigns.ts`): deterministic thresholds — an in-flight (`sending`) message with no DB progress for **15 minutes** is presumed lost (worker crash/redeploy) and re-finalized through the _existing_ `finalize_email_message` RPC with the fixed code `worker_stalled` (correct counters + capacity release, no invented send state); a never-started `queued` campaign older than **24 hours** is cancelled through the existing `cancel_queued_campaign` RPC (releasing its reserved capacity). Recovery runs on **every** campaign access — the monitor page (`getCampaign`) and each worker tick (`processCampaignBatch`) — always scoped to the session user.

**Root error boundary** (`global-error.tsx`): the last missing boundary — a self-contained client component (it renders its own `<html>/<body>`) for root-level errors.

### API Abuse Protection & Security Headers (Phase 12)

The app exposes expensive or abuse-amplifying surfaces: the **BA jobs API runs under a shared public client id** (sustained per-user bursts can get the _whole app_ banned upstream), the AI chat costs per request, and account/admin endpoints are sensitive. Phase 12 adds server-side rate limiting with **no external dependency**:

- **Postgres fixed-window limiter** (`rate_limits` table + `check_rate_limit` RPC, migration 11): atomic `insert … on conflict … count + 1` (no lost-update race), wall-clock-aligned windows (deterministic across instances), self-cleaning (windows older than 2 h are pruned on each call — no cron needed).
- **Deny-by-default**: RLS is enabled on `rate_limits` with _no_ policies (nobody without BYPASSRLS sees rows), the RPC is `security definer` with execute **revoked from `public`/`anon`/`authenticated`** and granted to `service_role` only — the browser can neither read counters nor inflate/deflate them.
- **Per-session-user scopes** (key `scope:<session_user_id>` — never request-body ids): AI chat 20/min · opportunity search 10/min · opportunity save 10/min · email OAuth starts 5/min · data export 2/h · account deletion 5/h · admin actions 30/min.
- **Enforcement**: every protected route checks the limiter _after_ authentication, _before_ any business logic (tested: denied requests never reach the AI provider, the BA upstream, or the account/admin services). Denied → `429` + `retry-after` + `x-ratelimit-*` headers.
- **Fail-open policy (documented)**: if the limiter RPC itself errors, the request is allowed — the limiter is abuse protection, not the security gate (each route keeps its own authn/authz), and a limiter outage must never take the product down for all users.
- **Baseline security headers** (`next.config.ts`): `x-content-type-options: nosniff`, `x-frame-options: DENY`, `referrer-policy: strict-origin-when-cross-origin`, `permissions-policy` (camera/mic/geo/payment/usb denied) on every route. CSP completed in Phase 13 (below).

### Content Security Policy & Security Policy Audit (Phase 13)

Phase 12 deferred the CSP until the app's browser-side origin surface was fully audited. Phase 13 performs that audit against the code and ships a strict, tested policy:

**Origin audit (verified facts, not assumptions):**

- The browser talks to exactly **two** origins: the app itself and the Supabase project (auth + REST + storage via `supabase-js`).
- **All** other integrations — OpenAI, Google/Microsoft OAuth, the BA jobs API — are server-side only. OAuth provider domains appear exclusively as top-level redirects, which CSP does not constrain.
- No web fonts (`next/font` unused), no third-party scripts, no WebSockets/realtime, **zero** `dangerouslySetInnerHTML`, and no storage/signed URLs are ever exposed to the client (file content flows through same-origin API routes).

**The policy** (`buildSecurityHeaders` in `src/lib/security-headers.ts`, consumed by `next.config.ts`, asserted by tests): `default-src 'self'`; `connect-src 'self' <supabase-origin>`; `img-src 'self' data: blob:` (inert schemes only); `style-src 'self' 'unsafe-inline'`; `script-src 'self' 'unsafe-inline'`; `object-src 'none'`; `frame-ancestors 'none'`; `base-uri 'self'`; `form-action 'self'`; `upgrade-insecure-requests`. `'unsafe-eval'` appears nowhere (test-enforced).

**Documented trade-off:** `script-src` carries `'unsafe-inline'` because Next 16.3.x provides **no CSP nonce support** for App Router RSC payload scripts (verified in the installed `next` dist). React 19 escapes all rendered output and the app has no `dangerouslySetInnerHTML`, so the residual risk requires a prior content-injection bug. Nonce-based `script-src` is the documented next hardening step.

**Fail-safe env handling:** the Supabase origin is derived at **build time** from `NEXT_PUBLIC_SUPABASE_URL` (a public-by-design env var — no secret ever enters the header). A malformed/missing value degrades to `connect-src 'self'` — never a broken or attacker-influenced directive (tested).

**Deployment implication:** the CSP bakes in the Supabase origin at build time. If the Supabase project URL ever changes, **rebuild** the app (the header is static per build, like all `next.config` headers).

### Durable Email Worker (Phase 14)

The sending engine was correct but not **operationally durable**: the processing endpoint takes an explicit `(user_id, campaign_id)`, and nothing could _discover_ which campaign was due next — a freshly deployed or crash-recovered worker had no way to start work on its own. Phase 14 closes that inside Postgres, with **no external queue/scheduler product introduced**:

**The contract** (any poller — cron, container loop, queue consumer):

```
loop:
  1. POST /api/internal/email-worker/claim   (x-email-worker-secret)
       → { campaign: { userId, campaignId } }  |  { campaign: null }
  2. if campaign: POST /api/internal/email-worker (same secret)
       { userId, campaignId, batchSize? (≤5) }
  3. sleep (e.g. 5–15 s); repeat
```

- **Discovery**: `claim_next_pending_campaign` RPC — a campaign is due iff it is non-terminal (`queued`/`sending`) and has ≥1 message `queued` and due (`next_attempt_at` null or past). FIFO by `created_at`. `FOR UPDATE … SKIP LOCKED` means concurrent pollers never receive the same campaign in the same instant — with N pollers, work fans out across campaigns.
- **Why no double-send**: the campaign claim is only _discovery_; the actual work item (each message) is still claimed atomically per message by the existing `claim_next_email_message` (`SKIP LOCKED`). Two pollers processing the same campaign concurrently always claim **different** messages. Duplicate/overlapping polls are therefore harmless by construction (idempotent discovery, exclusive per-message execution).
- **Crash/retry semantics (at-least-once, defined window)**: if a poller dies between claiming a message and finalizing it, the message stays `sending`; Phase 11 recovery re-finalizes it as failed with `worker_stalled` after 15 min (counters + capacity restored). If the provider call actually succeeded in that window, the user sees a _reported failure for a possibly-delivered email_ — standard at-least-once mail semantics; resends may duplicate, never silently lose. The window is bounded and deterministic, never silent.
- **Bounded execution**: batch size clamped to ≤5 per call; provider timeouts bound each send; the poller loop bounds everything else. No unbounded work.
- **Health/readiness**: `GET /api/health` (public, `no-store`) → `{ status: "ok"|"degraded", checks: { database, workerSecretConfigured } }`, 200/503. **Booleans only** — no env values, no error details, no user data (tested). Deployment monitoring is now a URL, not a guess.

### Email Account Lifecycle (Phase 15)

Audit finding (fixed in this phase): `email_campaigns.email_account_id` was `NOT NULL` + `ON DELETE RESTRICT`, so **any user who had ever created a campaign could never disconnect their email account** — the delete failed with a raw FK violation that surfaced as a generic "disconnect_failed". Users with a draft on the sender were equally stranded, and the disconnect action had no test coverage.

**The lifecycle policy now (all server-derived, tested):**

- **Active campaigns block** — disconnect is refused with `active_campaigns` while the sender has `queued`/`sending` campaigns (cancelling first stays the user's explicit choice — the app never cancels for them).
- **Drafts block** — refused with `drafts_in_use` while any draft uses the sender (a draft must keep its sender to stay sendable). Since Phase 18 the block is resolvable in place: the email settings page lists the blocking drafts and offers `reassignDraftSender` — a server action that verifies both the draft's and the destination account's ownership (user-scoped, both sides) and updates **only** `sender_email_account_id`, after which the unchanged disconnect flow proceeds.
- **Terminal history no longer blocks** — `email_campaigns.email_account_id` is now nullable with `ON DELETE SET NULL` (migration 11): completed/partially-failed/cancelled campaigns keep all their data and only lose the sender pointer when the account is deleted. This also makes GDPR account deletion strictly more robust (no RESTRICT ordering risk).
- **No partial disconnect** — the guards run _before_ any revoke/delete (tested); a blocked disconnect revokes nothing.
- **Proactive UI** — each connected account shows a server-computed "In use" badge (active campaigns / drafts) and a disabled Disconnect button with the reason; the server remains authoritative.
- **Defensive invariant** — `processCampaignBatch` now fails loudly and deterministically if an _active_ campaign ever lacks a sender (unreachable by design; the guard makes the invariant explicit instead of crashing deep in provider code).

### Item-Level Data Erasure (Phase 16)

Phase 11 gave users **whole-account** erasure; the audit for this phase found that **item-level** erasure was incomplete or unsafe: the AI file delete endpoint deleted the storage object **before** the database row (a RESTRICT FK violation would orphan the row, and a row failure would orphan the object), conversation deletion cascaded its rows but left the referenced storage objects behind, and there was **no way at all** to delete a single scan (uploaded CVs + extracted profile), a single AI-generated file, or an application draft. Phase 16 closes all of it — **no migration required** (every cascade/RESTRICT it relies on already exists in the schema; the FK topology is guarded by tests).

**The erasure contract (uniform across all five paths):**

1. **Authenticate + verify ownership server-side** on the exact item (user-scoped single-row lookup; unknown or foreign id → 404 / "not found", never a detail leak).
2. **Guard shared references first** — an upload still referenced by any scan is refused (409) before anything is touched.
3. **Delete the database row** (FK cascades remove the dependent rows: candidate profile, scan files, conversation messages, draft recipients/attachments).
4. **Sweep storage best-effort** — the DB row is the erasure commitment; an object that survives a transient storage failure is still swept by account deletion (paths are prefixed to the user). No storage sweep runs before the row is gone (no orphan states in either direction).

**The paths (all tested, including failure + security cases):**

- **Scan** — `deleteScan` (`bewerbung-scanner.ts`) + `DELETE /api/bewerbung-scanner/[id]` + the results page "Delete personal data" danger zone (two-step confirm → `deleteScanAction`). Cascades `candidate_profiles` + `bewerbung_scan_files`; then, for each upload that **no longer has any scan reference**, deletes the `ai_file_uploads` row + storage object. Uploads shared with another scan are kept (the same CV can legally back two scans). Returns `filesRemoved`.
- **AI upload file** — `deleteAIFile` (`ai-service.ts`) + rewritten `DELETE /api/ai/files` (strict `z.object({fileId: uuid}).strict()` — an injected `user_id` is a 400). Safe sequence: user-scoped lookup (`AIFileNotFoundError` → 404) → head-count of referencing scan files (`AIFileInUseError` → **409, nothing deleted**) → row delete → storage sweep.
- **AI-generated file** — new `DELETE /api/ai/generated/[id]` (session auth, UUID regex before any DB access, user-scoped row, delete-then-sweep).
- **Conversation** — `deleteConversation` now collects the storage paths of `ai_message_files` (resolved through the conversation's message ids — the table has no `conversation_id` column) and `ai_generated_files` **before** the cascade and sweeps them afterwards.
- **Draft** — `discardDraft` server action (`applications/new/actions.ts`) + composer danger zone (two-step `DiscardDraftButton`). Collects all attachment storage paths, deletes the draft row (cascades recipients + attachments), sweeps `application-attachments`. A draft referenced by an `email_campaigns` row is blocked by the existing FK `RESTRICT` (surfaced as a generic error — no data loss, no detail leak).

**Browser trust model:** the two-step confirm buttons are UX only — every erasure is a server action / API route that re-validates the session and item ownership, and the UI never receives storage paths, FK names, or error details beyond a fixed set of user-facing messages.

_(Phase 17 note: `removeAttachment` in the composer — the one erasure path still ordered storage-first — was re-ordered to the same row-first contract; its ordering is now pinned by tests.)_

### Storage Orphan Reconciliation (Phase 17)

Every erasure path is **row-first with a best-effort storage sweep** (Phase 16 contract): a transient storage failure, a crash inside the storage-first upload window, or any pre-Phase-16 conversation deletion can leave a storage object whose database row is gone. For **active** accounts, only whole-account deletion would ever reclaim such an object — meaning a CV the user deleted could sit in private storage indefinitely. Phase 17 adds the scheduled janitor that closes this gap, extending the existing provider-neutral worker contract — **no migration** (pure reads over existing tables + the storage `list`/`remove` calls already proven by the account-deletion sweep) and **no new environment variable** (same `EMAIL_WORKER_SECRET` trust boundary: the poller operator is service-level trusted anyway).

**The endpoint** — `POST /api/internal/storage-reconcile` (secret-gated, strict body `{ execute?: boolean, maxDeletes?: 1..100 }`):

```
periodic tick (e.g. hourly), same poller secret:
  POST /api/internal/storage-reconcile
    {}                          → dry-run report (DEFAULT — deletes nothing)
    { execute: true }           → delete up to maxDeletes (≤100, server-clamped)
  → { dryRun, maxDeletes, gracePeriodHours, buckets: [ { scanned, referenced,
      orphans, tooYoung, unknownPrefix, missingObjects, wouldDelete, deleted,
      deleteErrors } ] }
```

**The per-bucket algorithm** (`src/lib/storage-reconcile.ts`, for `ai-files` and `application-attachments`):

1. **Paginated reference collection** — union of `storage_path` over the bucket's keeping-alive tables (`ai_file_uploads` + `ai_message_files` + `ai_generated_files` / `application_draft_attachments`), read in 1000-row pages. A PostgREST row cap can therefore never hide a live reference (an unseen reference would mean deleting a live file — the one outcome this job must not have).
2. **Per-user-prefix listing** — for each `profiles` id (paginated), `storage.list` with `search: "{userId}/"` (the same proven pattern as the account-deletion sweep) plus a defensive `startsWith` filter, so one user's scan never sees another user's objects.
3. **Classification** — referenced (kept) / **age grace** (objects < 24 h old or undated: never deleted — protects the storage-first upload window) / **prefix gate** (not under a `{user-uuid}/` path: reported as `unknownPrefix`, never touched) / orphan.
4. **Double-check before delete** — references are re-collected immediately before any removal; a row that appears between scan and delete wins (tested with a simulated race).
5. **Bounded, reported deletion** — at most `maxDeletes` per tick in ≤100-object batches; a failed batch is counted (`deleteErrors`) and retried next tick, never thrown.
6. **Loud failure** — any database read or storage **list** error aborts the entire tick with a generic 500: the job only ever deletes on complete, freshly-verified knowledge.

**Diagnostics, not fixes** — `missingObjects` counts rows referencing objects that are absent from storage (e.g. a failed upload whose compensation also failed); it is reported for observability and never "fixed" by the janitor. Residual limitation: objects under prefixes of already-deleted accounts (a storage failure _during_ account deletion) are not enumerated — they are rare, the account is gone, and whole-account deletion already sweeps them best-effort.

**The ordering fix** — `removeAttachment` (composer attachment removal) was the last path still deleting the storage object **before** the row; a row-delete failure there left a dangling attachment row (UI showed an attachment whose object no longer exists). It now follows the Phase 16 contract: row delete first (the erasure commitment), best-effort storage sweep second — and any object a failed sweep leaves behind is exactly what this janitor reclaims.

### Security model

- **RLS** on every user table; the app only ever uses the service role for server-side writes that RLS would block (quota counters, encrypted tokens).
- **OAuth tokens** are stored AES-256-GCM encrypted; the encryption key lives in `process.env` only.
- **Server-only imports** (`server-only`) guard every file that touches the service role, AI keys, or OAuth secrets.
- **AI output** is treated as untrusted: every response is parsed against strict Zod schemas before it is stored or rendered; user documents are injected as untrusted data in the prompt.
- **Attachments** go to private storage buckets scoped by `user_id`; the browser only ever sees opaque upload IDs.
- **Application prefill** is derived exclusively from the server-side validated source: the browser never supplies recipient, company, title, salary, or `user_id`; the opportunity key is validated before any provider request and the opportunity is re-resolved server-side on every prefill.
- **Billing & admin** (Phase 10): plan, quota, and entitlement state is read only from persisted server-side data (`billing_plans`, `subscriptions`, `daily_usage`); the browser can supply none of it. Users have read-only RLS access to their own subscription row and **zero** access to `admins` / `admin_audit_log`; every admin action is session-verified, strict-schema-validated (injected `user_id`/entitlements → 400), service-role-scoped to the exact target, and written to the immutable audit log. The billing provider is deliberately unconfigured — the webhook seam answers 501 rather than faking validation.
- **Matching engine** is fully server-derived: the browser never supplies `user_id`, the candidate profile, an opportunity snapshot, a score, or reasons. The user id comes from the authenticated session, the profile from the user's own `candidate_profiles` row (RLS + `user_id`-scoped reads), and the opportunity from the authoritative provider (re-resolved, never from URL data). Match results are never written to the shared opportunity cache (user-independent key + `match: null` window — tested), and per-user snapshots live only in the user-scoped `saved_opportunities` rows. The save API accepts only `opportunityKey` + `notes` (strict schema; injected scores/titles are rejected — tested).
- **GDPR & deletion** (Phase 11): export/deletion act on the session user only. The delete endpoint uses a strict schema (injected `user_id` etc. → 400) and requires the typed email to match the session profile; the export never queries `email_accounts` (tokens/encrypted credentials); deletion aborts before the storage sweep when a database step fails (no partial data loss — tested); stale-campaign recovery only ever touches the session user's own campaigns and reuses the quota-safe existing RPCs.
- **Rate limiting** (Phase 12): limit keys are `scope:<session_user_id>` — the user id always comes from the authenticated session, never from the request; the `rate_limits` table is RLS-locked (no policies) and the RPC is executable by `service_role` only (revoked from `public`/`anon`/`authenticated`), so counters cannot be read or manipulated from the browser; window/limit bounds are validated server-side in the RPC. The limiter is deliberately fail-open (documented) — every protected route still enforces its own authn/authz independently.
- **CSP** (Phase 13): the policy is a tested pure function (`src/lib/security-headers.ts`) wired into `next.config.ts` — a wiring-guard test fails if the config ever drifts from the builder. Only the public `NEXT_PUBLIC_SUPABASE_URL` origin may extend `connect-src`; malformed values fail closed to `'self'`. Effects: third-party script/connect channels blocked, no framing, no object embedding, no base-tag hijack, same-origin forms, forced HTTPS. `script-src 'unsafe-inline'` is the one documented exception (no framework nonce support in Next 16.3.x — see Phase 13 section).
- **Worker discovery** (Phase 14): `claim_next_pending_campaign` is `security definer` with execute revoked from `public`/`anon`/`authenticated` (granted to `service_role` only) — the browser can neither enumerate due campaigns nor skip the queue; the claim endpoint accepts an **empty strict body** (the worker supplies nothing it controls) under the same `EMAIL_WORKER_SECRET` gate as processing; `/api/health` is public by design and returns booleans only (no secret values, no error details — tested).
- **Email lifecycle** (Phase 15): disconnect guards are server-derived usage counts (`user_id` + account-scoped head queries) — the browser never reports "in use"; a blocked disconnect performs **no** revoke/delete (no partial state); DB/FK failure details never reach the UI (generic message, tested); `SET NULL` (not cascade) means disconnecting a sender can never delete campaign history, and the drafts FK keeps its intentional `RESTRICT` (drafts need a live sender to stay sendable).
- **Item-level erasure** (Phase 16): every erasure path re-verifies item ownership server-side (user-scoped lookup; foreign/unknown id → 404, no detail leak); the AI file delete body is a strict `{fileId: uuid}` schema (injected `user_id` → 400, tested); the **409 in-use guard runs before any mutation** (a scan-backed upload can never be half-deleted); **row deletion always precedes the storage sweep** (no orphan rows, no orphaned objects left by a failed delete); shared uploads survive scan deletion (reference-counted head query, tested); the scan/draft server actions swallow only their own not-found/failure cases into a fixed redirect — DB/FK details never reach the UI; storage sweep failures are best-effort by documented design (the DB row is the erasure commitment; account deletion sweeps the user prefix regardless).
- **Storage orphan reconciliation** (Phase 17): the janitor sits behind the same `EMAIL_WORKER_SECRET` worker trust boundary (no session, no per-user auth — it is a service-level maintenance operation), with a **strict body and dry-run default** (deletion requires explicit `execute: true` from the operator's poller); the deletion budget is server-clamped (≤ 100, the storage batch limit); objects are only ever deleted when (a) under a valid `{user-uuid}/` prefix of a known profile, (b) at least 24 h old (undated = never), (c) unreferenced in a **paginated** full reference read, and (d) still unreferenced in a **fresh re-read immediately before removal**; a failed storage list or DB read aborts the whole tick (500, generic message) rather than acting on partial knowledge, and remove failures are reported per batch and retried next tick. The response is only ever sent to the secret holder (paths are service-trust data, never user-facing).
- **Draft reassignment** (Phase 18): `reassignDraftSender` re-verifies **both** ownerships server-side from the session (the draft via `assertDraftOwnership` and the destination via `assertSenderOwnership`, each user-scoped) before a single-column `UPDATE … WHERE id AND user_id`; a client-supplied `user_id` is never trusted. Both ids must be UUIDs before any DB access, and every rejection (foreign/missing draft, foreign/missing/inactive account, DB error) collapses to one fixed redirect (`error=reassign_failed`) — no ownership oracle, no DB/FK/internal detail leaks. The update is one atomic single-column statement, so it cannot half-apply (subject/body, recipients, attachments, and opportunity data are separate rows/columns and are never touched); campaigns are untouched and keep their own sender, so the active-campaign disconnect block is preserved.
- **Scanner bulk deletion** (Phase 19): `bulkDeleteScans` reuses the Phase 16 `deleteScan` erasure for each selected scan, adding a two-phase server gate on top. **Phase 1** ownership-verifies the _entire_ selection (`assertScanOwnership`, user-scoped) before any destructive operation, so a single foreign/missing id rejects the whole selection and a mixed owned + foreign selection can never be partially executed. **Phase 2** then runs the existing per-scan erasure (FK cascades, shared-upload retention, row-before-storage ordering). All `scanId`s and the `currentScanId` must be UUIDs before any DB access; empty selections and selections over the server cap (`BULK_DELETE_MAX_SCANS = 25`, checked on the raw entry count so id-spam can't amortize it) are rejected with zero operations; the current page's own scan can never be bulk-deleted. A client-supplied `user_id` is never trusted, storage failures remain best-effort (Phase 16), a mid-bulk database failure stops the loop and leaves the rest untouched (no unsafe storage deletion), and every failure collapses to one fixed redirect (`error=bulk_failed`) — no ownership oracle, no DB/FK/storage detail leaks.

## Known limitations

1. **Email sending needs a running poller** (deployment task, not a code gap) — the worker _contract_ is complete and provider-neutral since Phase 14 (discover via `/api/internal/email-worker/claim` → process → loop; monitor via `/api/health`). Any durable poller (cron, container loop, queue consumer) satisfies it; in development, run one manually or via a local cron. Since Phase 11, stuck states do not persist silently: in-flight messages stalled for >15 min and never-started `queued` campaigns >24 h are recovered automatically on the next worker tick or when the user opens the campaign monitor. Since Phase 17, the same poller (or any cron) additionally calls `/api/internal/storage-reconcile` on a low-frequency cadence so deleted personal data (e.g. CVs) is not left in storage indefinitely when a best-effort sweep fails.
2. **Opportunities search UX (Phase 3), the production matching engine (Phase 7, building on Phase 5), application prefill (Phase 6), and the Phase 8 dashboard intelligence are complete** — Step 9 of the roadmap is done and the end-to-end workflow (profile → search → matching → saved → prefill → composer → campaign → email) is connected through the dashboard. The BA API surface that works was live-verified: `v6/jobs` search, `v4/jobdetails`, `wo`/`umkreis`/`was`/`angebotsart`, and `veroeffentlichtseit=1` (today). The REST API does **not** support remote (`arbeitszeit`), free-text role (`beruf`), or company (`arbeitgeber`) filters — those are applied server-side on the normalized source data via a bounded scan (surfaced as `scan_truncated`). The source also only exposes its first ~10,000 listings per query (deeper `page*size` return empty pages), so pagination is capped at 200 pages × 50 items and the bound is surfaced instead of faked.
3. **Source data limits what the matcher can verify (never faked).** The BA source does not today provide structured skills or language requirements, so those dimensions are usually `not_applicable` and drop out of the score (renormalized). The candidate profile schema has no working-time preference field, so the employment dimension is always `unknown`. The BA source documents **no industry field**, so the user-preferences dimension is `unknown` (non-essential) when the candidate documents industry preferences and `not_applicable` otherwise. The profile schema has **no training-type preference** field, so the training-type dimension is `unknown` (non-essential) for offers where the source documents an Ausbildungsform. Experience is only compared when the source explicitly states "N Jahre Erfahrung". Relocation willingness is documented generically (not per city), so a willing profile yields `partial` — never a full match. The remote preference is free text and parsed with a documented heuristic.
